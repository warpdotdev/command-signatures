# Technical design: conflicting short-flag validation

## Current behavior
`completion-metadata/src/fig_types.rs` defines `CommandOption.name` as one or more strings. `From<CommandOption> for Opt` applies `html_unescape` to every authored name before storing it in `Opt.exact_string`. `From<Command> for Vec<Signature>` recursively converts command nodes and copies persistent options into child commands during conversion.

`completion-metadata/src/signature.rs` already classifies short flags in `is_short_hand_flag` and exposes converted short flags through `Signature::short_hand_flags`. The classifier is currently private, and neither conversion nor the command-signature crate checks whether distinct options claim the same short flag.

Repository invariants live in the test module in `command-signatures/src/lib.rs`. Its tests deserialize embedded specs, verify generator references, and reject unsafe generator newlines. `script/presubmit` runs formatting, Clippy, and `cargo test`; `.github/workflows/CI.yml` also has a `cargo test --verbose` job. No separate validation command or fixture tree exists.

`command-signatures/src/assets.rs` deliberately combines handwritten and autogenerated assets for runtime lookup, so the existing `commands()` iterator is not an appropriate discovery source for a handwritten-only rule. It also returns post-conversion `Signature` values, which have lost the source option boundaries needed for precise diagnostics.

## Proposed implementation
### Shared metadata validator
Add a small validation module in `completion-metadata`, operating on `fig_types::Command` before conversion. It should:

1. recursively walk the root command and all `subcommands`;
2. build a canonical path from the first name declared at each level;
3. inspect only the current node's `options`;
4. transform each option name with the same HTML-entity unescaping used by `From<CommandOption> for Opt`, then classify that normalized spelling with the existing short-hand classifier;
5. group occurrences by short flag while deduplicating repeated occurrences from the same option entry;
6. emit one structured conflict per flag claimed by at least two option entries.

The structured conflict must retain the canonical command path, normalized short flag, each option's zero-based source index for programmatic use, and each option's complete raw name list. Formatting converts indices to one-based positions and displays raw name arrays exactly as authored; this makes an encoded source such as `&#45;h` findable while the normalized `-h` identifies the runtime collision. File paths belong to the caller because `fig_types::Command` does not know its source.

Move or expose `html_unescape` and `is_short_hand_flag` within the crate so validation and conversion share the same normalization and classification implementations. Do not publish duplicate helpers with subtly different entity, Unicode, or dash behavior.

The recursive walk and diagnostic types should be reusable by the duplicate-name work in #399. That issue can add another rule over the same command/option traversal, but duplicate full-name validation is not implemented under #400.

### Handwritten-spec invariant
Add an invariant test in `command-signatures/src/lib.rs` that reads only the top-level `command-signatures/json/*.json` files from `CARGO_MANIFEST_DIR`, deserializes each into `fig_types::Command`, calls the shared validator, attaches the repository-relative file path, and sorts the collected conflicts deterministically.

Do not use `Assets::iter()` or `commands()` for this test: both combine manual and autogenerated assets, and `commands()` validates converted rather than authored option sets.

The test compares complete collected conflict records with a constant baseline of the 45 current `(relative file, canonical command path, normalized short flag)` keys and each key's ordered claimant list of source indices and complete raw `name` arrays:

- Any collected conflict key absent from the baseline fails with the complete diagnostic.
- Any existing key whose ordered claimant list differs from its baseline fails and shows the expected and actual claimants. Adding a claimant, removing one, reordering options, or swapping a claimant is therefore review-visible even when the key is unchanged.
- Any baseline conflict absent from the collected set fails as stale and tells the contributor to remove it.
- Only records matching both the key and ordered claimant list avoid failure.
- The baseline is documented as temporary and links the dedicated cleanup issue required by the product rollout.

This complete-record comparison makes the allowlist non-expandable by accident and guarantees monotonically reviewed burn-down. Adding or changing an entry remains possible only as an explicit code-review decision; baseline content must not be generated automatically during tests.

### Diagnostic formatting
Formatting must be deterministic and use this shape:

`<relative file>: command "<canonical path>": duplicate short flag "<flag>" is used by options #<position> <JSON name array>[, ...]`

Display the normalized short flag but use the raw authored name arrays in JSON formatting so aliases, entities, and punctuation are unambiguous and findable in source. List conflicting options in source order. Aggregate all unexpected or changed conflicts into one assertion failure so contributors can fix every reported location in one pass.

## Fixture and test coverage
Create focused JSON fixtures under `completion-metadata/tests/fixtures/duplicate_short_flags/` and exercise them from validation tests.

Invalid coverage:

- two differently named option entries on one command share one short flag;
- two distinct entries have identical complete name arrays, proving positions distinguish them;
- three option entries share one short flag and produce one diagnostic listing all three;
- a duplicate exists on a nested subcommand and the diagnostic contains the full root-to-leaf path;
- an option repeats the same short spelling internally and another option claims it, proving the first option is counted once rather than creating pairwise duplicate diagnostics.
- one option spells `-h` as `&#45;h` and another spells it literally, proving runtime-equivalent names conflict and the diagnostic displays normalized `-h` with both raw arrays.

Valid coverage:

- every option on one command has a distinct short flag;
- root options and child options reuse a short flag;
- sibling subcommands reuse a short flag;
- unrelated top-level fixture commands reuse a short flag;
- one option contains a short and long alias without conflict;
- names classified as long flags (`--help` and `-version`) do not participate in the short-flag rule;
- a command or subcommand name array is treated as aliases for one namespace.

The command-signature crate should also test file discovery boundaries: a fixture or helper-level test confirms that only top-level handwritten JSON is selected, not `autogenerated/` or `overrides/`.

The baseline comparison must have regression tests in which an otherwise matching baselined key gains a third claimant and in which one claimant is replaced. Both cases must fail because their ordered claimant records differ even though `(file, command path, short flag)` is unchanged.

## Edge cases
- Report one conflict per command namespace and short flag, not one error per pair of options.
- Preserve case. `-v` and `-V` are different flags.
- Decode HTML entities exactly once through the shared conversion helper before classification; apply no other normalization. Diagnostics preserve raw authored names while identifying the normalized conflicting flag.
- A duplicate spelling inside one option entry alone is not a #400 conflict.
- Parent and child nodes are independent even when the parent option is persistent. The validator runs before persistent-option expansion and does not report the inherited copy as another authored option.
- If a node has multiple command names, its options are validated once and its first declared name is used in the canonical path.
- Existing malformed JSON remains the responsibility of deserialization validation; the new validator receives a successfully deserialized `Command`.

## Verified baseline
The inventory was recomputed against `origin/main` commit `d69b340ef622540ac28340ef565dae45287d51d8` by recursively examining the directly declared options of every `command-signatures/json/*.json` command node, HTML-unescaping names before short-flag classification, and excluding `autogenerated/` and `overrides/`. Runtime-equivalent normalization does not change the verified total or distribution.

The 45 keys are distributed as follows:

- `brew.json`: `brew services` (`-v`, `-h`)
- `copilot.json`: 27 `-n` conflicts across `svc`, `job`, `task`, `deploy`, and mirrored `help` descendants
- `flutter.json`: `flutter assemble` (`-d`), `flutter symbolize` (`-d`)
- `kubecolor.json`: `kubecolor expose` (`-l`)
- `kubectl.json`: `kubectl expose` (`-l`)
- `oc.json`: `oc expose` (`-l`)
- `pscale.json`: `pscale completion` (`-h`), `pscale connect` (`-h`)
- `pulumi.json`: `pulumi import` (`-f`)
- `rsync.json`: `rsync` (`-h`)
- `sfdx.json`: `sfdx auth:accesstoken:store` (`-s`)
- `stripe.json`: `stripe events resend`, `stripe get`, `stripe post`, and `stripe delete` (`-v`)
- `yarn.json`: `yarn` (`-s`)
- `zapier.json`: `zapier-platform-cli scaffold` (`-d`)

## Validation commands
The implementation must pass:

- focused validator tests for all valid and invalid fixtures;
- `cargo test --verbose`;
- `cargo clippy -p warp-command-signatures -p warp-completion-metadata --all-targets --all-features -- -D warnings`;
- `cargo fmt -p warp-command-signatures -p warp-completion-metadata --check`;
- `script/presubmit`.

No change to `script/presubmit` or `.github/workflows/CI.yml` is required because both already invoke the selected test path.

## Implementation boundaries
Expected implementation areas are `completion-metadata/src/signature.rs`, a new validation module exported from `completion-metadata/src/lib.rs`, focused fixtures/tests in `completion-metadata/tests/`, and the invariant test in `command-signatures/src/lib.rs`.

The implementation must not modify command JSON, autogenerated output, overrides, completion parsing behavior, or Warp UI code as part of #400.
