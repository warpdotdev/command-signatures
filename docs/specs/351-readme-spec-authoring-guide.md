# Spec: Document the JSON spec schema and contribution workflow in the README

**Issue**: [#351](https://github.com/warpdotdev/command-signatures/issues/351)
**Status**: Draft for maintainer review

## Problem

The README documents where command signature specs live (`command-signatures/json/*.json`) and explains the autogenerated spec override system, but it does not document:

1. The JSON schema fields contributors need when hand-writing a spec
2. The recommended workflow for adding a new hand-written spec

New contributors must reverse-engineer the schema from existing files, which raises the contribution barrier.

## Proposed Solution

Add a "Writing a new spec" section to the README covering:

1. Top-level JSON structure with an annotated minimal example
2. Required vs optional fields (derived from the Rust types)
3. Naming conventions (file name matches command name)
4. Local validation workflow

### Recommendation: Approach

**Recommendation**: Write a concise contributor-facing section directly in the README, not a separate `CONTRIBUTING.md`.

**Rationale**:
- The repo has no existing `CONTRIBUTING.md` and only three markdown files at the root (`README.md`, `AGENTS.md`, `LICENSE.md`)
- A self-contained README section is discoverable without adding another file to navigate
- The existing agent skill at `.agents/skills/add-command-spec/SKILL.md` is comprehensive but AI-facing; duplicating it for humans risks drift

**Duplication mitigation**: The README section should be a stable, minimal reference. Advanced workflows (Fish shell research, platform-specific generators, screenshot requirements) remain in the agent skill. The README explicitly notes that agent-assisted contribution is available via the skill.

### Command (top-level object)

| Field | JSON key | Type | Required | Notes |
|-------|----------|------|----------|-------|
| `name` | `name` | `string` or `string[]` | **Yes** | Only truly required field; accepts single string or array for aliases |
| `description` | `description` | `string` | No | Defaults to empty string via `#[serde(default)]` |
| `subcommands` | `subcommands` | `Command[]` | No | Nested commands; empty array default |
| `options` | `options` | `CommandOption[]` | No | Flags and options; empty array default |
| `args` | `args` | `Arg` or `Arg[]` | No | Positional arguments; accepts single object or array |
| `parserDirectives` | `parserDirectives` | `ParserDirectives` | No | Parsing behavior overrides |
| `aliasGenerator` | `aliasGenerator` | `string` | No | Reference to a Rust alias generator |
| `isDangerous` | `isDangerous` | `bool` | No | Default `false` |
| `priority` | `priority` | `number` | No | Fig priority (50 = default) |
| `hidden` | `hidden` | `bool` | No | Default `false` |

### Template values

Valid `template` values (from `enum Template`, lines 283-302):
- `"filepaths"` — existing files
- `"filepathsMayNotExist"` — files that may not exist yet
- `"folders"` — existing directories
- `"foldersMayNotExist"` — directories that may not exist yet
- `"history"` — command history (ignored by Warp)
- `"help"` — help text (ignored by Warp)

## Proposed README Section

The following section would be added to `README.md` after the "Overriding Autogenerated Commands" section:

---

### Writing a New Spec

Hand-written specs live in `command-signatures/json/<command>.json`. The file name must match the command name.

#### Minimal Example

```json
{
    "name": "mycommand",
    "description": "Short description of the command",
    "options": [
        {
            "name": [
                "-v",
                "--verbose"
            ],
            "description": "Enable verbose output"
        }
    ],
    "args": {
        "name": "file",
        "template": "filepaths"
    }
}
```

#### Required vs Optional Fields

Only `name` is required at the top level. All other fields default to empty/false.

For options, `name` is effectively required (an option without a name is meaningless).

Common optional fields:
- `description`: Short help text
- `options`: Array of flags/options the command accepts
- `args`: Positional argument(s); accepts a single object or an array
- `subcommands`: Nested commands (same structure as the top level)

For dynamic completions, use `generatorName` to reference a Rust generator, or `template` for built-in file/folder completion.

#### Subcommands

Subcommands nest inside the `subcommands` array, each with the same structure as the top-level command:

```json
{
    "name": "git",
    "subcommands": [
        {
            "name": "commit",
            "options": [
                {
                    "name": [
                        "-m",
                        "--message"
                    ],
                    "args": {
                        "name": "message"
                    }
                }
            ]
        }
    ]
}
```

#### Local Validation

Before opening a PR:

1. Install dependencies: `npm install`
2. Format the spec: `npm run format -- command-signatures/json/<command>.json`
3. Run the presubmit checks: `script/presubmit`

The presubmit script runs:
- `npm run format:check` (Prettier on JSON specs)
- `cargo fmt --check` (Rust formatting)
- `cargo clippy` (Rust lints)
- `cargo test` (including generator name validation)

Requires: Node.js for Prettier, Rust toolchain 1.92+ (see `rust-toolchain.toml`).

**Note on array formatting**: The repo uses `prettier-plugin-multiline-arrays` with `multilineArraysWrapThreshold: 1`, so any array with more than one element must be wrapped one element per line. Running `npm run format` will rewrite inline arrays like `["-v", "--verbose"]` to the wrapped form shown above.

## Annotated JSON Example

The following is a verified, complete example based on `command-signatures/json/kill.json`:

```json
{
    "name": "kill",
    "description": "Terminate or signal a process",
    "args": {
        "name": "pid",
        "isVariadic": true,
        "generatorName": "process"
    },
    "options": [
        {
            "name": "-s",
            "description": "A symbolic signal name specifying the signal to be sent",
            "args": {
                "name": "signal_name",
                "generatorName": "signal_name"
            }
        },
        {
            "name": "-l",
            "description": "If no operand is given, list the signal names; otherwise, write the signal name corresponding to exit_status",
            "args": {
                "name": "exit_status",
                "isOptional": true
            }
        }
    ]
}
```

Key observations:
- `name` is a string, not an array (single name, no aliases)
- `args` is a single object (could be an array if multiple positional args)
- `generatorName` references Rust generators defined in `src/generators/kill.rs`
- Options can have their own `args` for option arguments

## Assumptions Made

1. The README is the right location (no `CONTRIBUTING.md` exists, and this is a small addition)
2. A minimal example is more useful than an exhaustive schema reference
3. The Prettier formatting requirement should be documented since CI enforces it
4. First-time contributors may not have the Rust toolchain installed, so noting `rust-toolchain.toml` is helpful
